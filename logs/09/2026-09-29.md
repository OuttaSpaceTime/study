- **Question:** Why is calling `Rails.application.eager_load!` in a test a problem, and why is a route-path model-inferring test helper (constantize + `ApplicationRecord.descendants` demodulize fallback + reflection) worse than each test class defining `model`?
- **Wiki hits:** [[software-design/judging-abstractions]] (flag/branch accretion = wrong abstraction). No page on Zeitwerk/autoloading or `descendants`; [[rails/activerecord-preloading]] matched only the unrelated query method `eager_load`.
- **Card hits:** cmtmq761h00009o0mdc4w0g3d (shared function grew three boolean params, what to ask); cmr352oou0001vi0m2ma2kmqz (re-inline a wrong abstraction first). No cards on autoloading/eager loading/descendants.
- **Web check:** refines: Autoloading guide §10 confirms `subclasses`/`descendants` miss classes not yet loaded under lazy loading; Rails Testing guide §16 actually endorses `Rails.application.eager_load!` in a dedicated `ZeitwerkComplianceTest` (when there is no CI), so the problem is using it as a crutch for the `descendants` fallback, not the call itself; `ENV["CI"].present?` default dates from Rails 7 (still in the 8.1 template). Minitest `methods_matching` uses `public_instance_methods(true)` (confirmed in source). https://guides.rubyonrails.org/autoloading_and_reloading_constants.html#single-table-inheritance , https://guides.rubyonrails.org/testing.html#testing-eager-loading
- **Source:** mixed
- **Answer:** eager_load! only props up the `descendants` fallback (which sees loaded classes only), is slow locally and leaks global state; the helper is a convention-guessing engine whose branches mark where the convention broke, and demodulize matching can pick the wrong class; prefer a shared Minitest module of `test_` methods with each class defining `path`/`model` explicitly.
