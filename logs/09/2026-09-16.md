## Query 1 (06:03)
**Question:** sql/nullable-columns: when is it safe to migrate from NULL values to placeholders like empty string or infinity?
**Wiki hits:** [[sql/nullable-columns]] (covers 3VL, UNIQUE-vs-NULL, nullable FKs, "Sentinels Masquerading as Values" — same theme but framed as NULL-vs-sentinel-at-design-time, not the NULL-to-placeholder migration direction)
**Card hits:** none
**Web check:** refines: Kimball's unknown-member pattern also covers dimension attributes generally (not just nullable FKs), substituting descriptive sentinels like "Unknown"/"Not provided"/"Data not yet available" rather than leaving NULL, while NULL facts (measures) are fine to keep since aggregates handle them correctly; Postgres 14+ allows Infinity for an unconstrained NUMERIC (a NUMERIC with explicit precision/scale still errors on overflow); Oracle treats '' as NULL for VARCHAR2, the reverse gotcha — https://www.kimballgroup.com/2003/02/design-tip-43-dealing-with-nulls-in-the-dimensional-model/
**Source:** mixed
**Answer:** Migrating NULL to a placeholder (empty string, infinity, sentinel) is safe only when you control every consumer, the column represents a single unambiguous "no value" case, aggregates/sorting/uniqueness/comparison semantics won't be skewed by treating the placeholder as real data, and you lock in NOT NULL afterward; Kimball's "unknown member" dimension row is a sanctioned exception for nullable FKs.

**Change:** Fixed anki-sync deleting cards created on another machine, and made deletion propagate correctly across machines.

Root cause: `plan_sync` treated "CUID-tagged note on Anki with no master row" as an intentional deletion to propagate, with the sole exception of a completely empty master (`master_is_empty`). With two machines syncing through one AnkiWeb collection, that state is the *normal* shape of a card created on the other machine, so each machine deleted the other's new cards. The Session 5 fix only covered the total-wipe case.

Fix: deletion is now explicit state on both sides and is never inferred from absence. `delete_card`/`delete_cards` write a `DeletedCard` tombstone row in the same transaction that drops the card. The sync tags the Anki note `__deleted__` and suspends it rather than removing it, which is how a deletion reaches the other machines through the only channel they share. `plan_sync` gained a `deleted_ids` argument and now decides over the full local (LIVE/TOMB/NONE) x remote (LIVE/DEL/NONE) table, so `LIVE x NONE` can only mean "new here" and `NONE x LIVE` can only mean "created elsewhere". `SyncPlan.delete_notes` is gone, replaced by `tag_deleted` and `local_soft_delete`; `bridge.delete_notes` became `purge_notes` and is currently unused. `_gather` excludes deleted notes' reviews so they never try to land on a missing Card row. The sync stays stateless: no bookkeeping was added, every decision still derives from the current state of both sides.

**Why:** a dry-run before a requested sync showed `delete 8`, which was today's Sessions 2 and 6 work (3 SQL nullability cards, 5 database-index cards) created on the other machine. Pushing would have destroyed the only copy.
