## Query 1 (20:41)

- **Question:** How does Rails authentication normally work? Is it cookie-only, and why?
- **Wiki hits:** [[security/csrf]] (adjacent — covers session + secret_key_base in a CSRF context; no dedicated Rails session-store / authentication page exists)
- **Card hits:** none (multiple queries on "Rails session cookie", "signed encrypted session cookie replay", "secret_key_base CSRF session" all returned empty)
- **Web check:** confirms — CookieStore is "the default and recommended session store" (signed via secret_key_base; encrypted by default since Rails 4 when secret_key_base is set); other stores (CacheStore, ActiveRecordStore) keep only a session id in the cookie and store data server-side; HttpOnly is a session-store option (default on). Rails 8 `rails generate authentication` confirmed: DB-backed Session model with has_secure_token, plus a signed, permanent, HttpOnly token cookie (resume_session/find_session_by_cookie). Sources: https://guides.rubyonrails.org/action_controller_overview.html , https://guides.rubyonrails.org/security.html , https://blog.saeloun.com/2025/05/12/rails-8-adds-built-in-authentication-generator/
- **Source:** memory (web-confirmed)
- **Answer:** Rails default is CookieStore — the session hash is signed+encrypted with secret_key_base and lives in an HttpOnly cookie (no server-side table); cookies are used because HTTP is stateless and the browser auto-sends them; alternatives (ActiveRecord/Redis store, Rails 8's DB-backed Session model, API Bearer/JWT) trade cookie-only statelessness for server-side invalidation.
