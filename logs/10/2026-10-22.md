**Question:** Why can't the attacker just embed a script tag with a stolen nonce from the current script tags? (CSP nonces, strict CSP)
**Wiki hits:** none directly on nonces; nearest [[security/xss]] (CSP/XSS defence context), [[security/same-origin-policy]]
**Card hits:** cmqkr78xu0005yb0mcz8nk08i (why can't an injected payload read the current nonce to copy it); cmqkr7c6g0007yb0mhhuw37en (why reusing a leaked earlier nonce fails); cmqkr772h0004yb0mweyvp3j9 (why the nonce can't be guessed); cmqkr7aoj0006yb0mslqjly12 (why injection can't swap the header CSP); cmowkwfn7000brb0mkj8ky9r2 (three properties a nonce needs); cmowkwj7c000crb0mmzn3fei7 (where the nonce comparison happens); cmqdhhzim000h920manyyvmtv / cmqdhhwjw000g920m3j9xewob / cmnwwesob000dfb0mzr99cij5 (nonce vs hash)
**Web check:** refines: nonce hiding (content attribute blanked, only `.nonce` IDL keeps it) applies only when the CSP came from an HTTP header, not a `<meta>` CSP; "is element nonceable" applies to script elements and rejects attribute names OR values containing "<script", "<style" or "<link", plus duplicate-attribute parse errors, and is marked at-risk in the spec. Unique-per-response (MUST), base-uri 'none' for nonce retargeting confirmed. https://w3c.github.io/webappsec-csp/#is-element-nonceable , https://w3c.github.io/webappsec-csp/#security-nonces , https://html.spec.whatwg.org/multipage/urls-and-fetching.html#nonce-attributes
**Source:** mixed
**Answer:** Nonce is fresh per response and written after the payload, reading it from the DOM needs script already running, and browsers hide the nonce attribute; it breaks with static/cached nonces, dangling-markup nonce stealing (mitigated by "is element nonceable") and `<base href>` retargeting (fixed by base-uri 'none').

## Query 2 (09:11)
**Question:** In the examples, does the browser really send only one nonce? (CSP game: all of the page's legit scripts share one nonce value)
**Wiki hits:** none on nonce generation; nearest [[security/xss]] (CSP section)
**Card hits:** cmowkwfn7000brb0mkj8ky9r2 (three nonce properties: fresh per response, identical in header and every trusted tag); cmnwwesob000dfb0mzr99cij5 (one fresh token in header and every trusted tag); cmowkwj7c000crb0mmzn3fei7 (the browser does the comparison); cmqkr7c6g0007yb0mhhuw37en (fresh per response); cmne7xtp0018z0msol1amcijw ("nonces need syncing across app servers", which conflates CSP nonces with stateful form nonces)
**Web check:** confirms, with refines: CSP3 says the server "MUST generate a unique value each time it transmits a policy" (per response, not per element), and the source-list grammar allows several nonce-sources. Rails 8.0/8.1/main generator template, commented out: `config.content_security_policy_nonce_generator = ->(request) { request.session.id.to_s }` ("Generate session nonces..."). The Rails security guide shows `SecureRandom.base64(16)` as "a good default" (new nonce per request) and offers session.id only as the ETag-compatible alternative, "its security depends on the session id being sufficiently random and not being exposed". `request.content_security_policy_nonce` is memoized in a request env header, so one value per request is shared by every tag and the header. Golinelli et al. 2023 treat per-session nonce reuse as a recognised (weaker) flaw: 598 of 2271 nonce-CSP sites reused nonces. https://w3c.github.io/webappsec-csp/#security-nonces , https://github.com/rails/rails/blob/main/railties/lib/rails/generators/rails/app/templates/config/initializers/content_security_policy.rb.tt , https://guides.rubyonrails.org/security.html#content-security-policy-header , https://github.com/rails/rails/blob/main/actionpack/lib/action_dispatch/http/content_security_policy.rb , https://arxiv.org/abs/2309.07782
**Source:** mixed
**Answer:** The browser sends no nonce. The server makes one random nonce per response and puts it in the header and on every trusted tag, and the browser compares them. Sharing one value is normal and several nonce-sources are allowed. 'strict-dynamic' extends trust to scripts that nonced scripts insert. Rails' generated initializer uses request.session.id (per-session), flagged as unverified.

## Query 3 (09:27)
**Question:** Why does Rails suggest that? (the session-id nonce generator `request.session.id.to_s` in the generated CSP initializer)
**Wiki hits:** none
**Card hits:** cmowkwfn7000brb0mkj8ky9r2 and cmnwwesob000dfb0mzr99cij5 mention "every trusted tag" in their backs; no card front asks why one shared nonce per response is enough
**Web check:** refines. Template history confirmed: the template suggested `SecureRandom.base64(16)` from 2018 (31abee0341, for UJS) until DHH's PR #43227 (2021-09-19, 40b25fd4b8) replaced it with `request.session.id.to_s`. The stated reason there is ETags, not Turbo: "In order for CSP to work with Turbo and an import map, we need nonces to be generated, but if we use per-request nonces, we'll cause the default etags generated on the basis of the response html to constantly change... worth the slight security trade-off". So Turbo/importmap explains why nonces at all, and ETags explains why per-session. ETag mechanism confirmed: Rack::ETag sets a weak ETag from a SHA256 of the body. The guide's ETag text came in f5cf908122. The Turbo problem is real but unstated in the PR: Turbo re-creates inline scripts with the nonce from `<meta name="csp-nonce">` (getCspNonce in src/util.js), mergeHead swaps that meta to the new response's nonce, and the document keeps its first CSP, so per-request nonces get scripts blocked (hotwired/turbo#294, still open). https://github.com/rails/rails/pull/43227 , https://github.com/rails/rails/commit/40b25fd4b8 , https://github.com/rails/rails/commit/31abee0341 , https://github.com/rails/rails/commit/f5cf908122f9abec8907ddfcc743b3ff12c33a58 , https://github.com/hotwired/turbo/issues/294 , https://github.com/hotwired/turbo/blob/main/src/util.js , https://github.com/rack/rack/blob/main/lib/rack/etag.rb
**Source:** research
**Answer:** Two reasons. Caching: random nonces change the HTML every request, which breaks ETag/304, while the session id is stable. Turbo (flagged unverified): Turbo Drive keeps the first page's CSP, so per-request nonces on fetched scripts get blocked. Rails moved the template from SecureRandom.base64(16) to the session id. Tradeoff: security rests on the session id staying secret, plus the nonce-reuse risk.
